# CORS CONFIGURATION

## The Working CORS Solution

**CRITICAL:** Every API endpoint file in `/api/` folder MUST include these headers.

### Required Code Pattern:

```javascript
export default async function handler(req, res) {
  // CORS headers (same pattern as Money Page Doctor)
  res.setHeader("Access-Control-Allow-Origin", "*");
  res.setHeader("Access-Control-Allow-Methods", "GET, OPTIONS");
  res.setHeader("Access-Control-Allow-Headers", "Content-Type");

  // Handle preflight
  if (req.method === "OPTIONS") {
    return res.status(200).end();
  }

  // Only allow GET (or POST, depending on endpoint)
  if (req.method !== "GET") {
    return res.status(405).json({ error: "Method not allowed" });
  }

  // Rest of API logic here...
}
```

### What Each Header Does:

1. **`Access-Control-Allow-Origin: "*"`**
   - Allows requests from ANY domain
   - Enables local HTML files and deployed tools to call the API

2. **`Access-Control-Allow-Methods: "GET, OPTIONS"`**
   - Allows GET requests (data fetching)
   - Allows OPTIONS requests (CORS preflight checks)

3. **`Access-Control-Allow-Headers: "Content-Type"`**
   - Allows Content-Type header in requests

4. **OPTIONS Handler:**
   - Browser sends OPTIONS request before actual request (preflight check)
   - Must return 200 status immediately
   - If missing, all API calls will fail with CORS errors

### Why This Configuration Works:

- Vercel serverless functions require explicit CORS headers
- Without these headers, browser blocks all cross-origin requests
- `"*"` origin allows tools to work from any domain (local, Vercel, future custom domain)
- This pattern was tested and confirmed working across all tools

# TOOL DEVELOPMENT WORKFLOW

## Standard Process for Building New Tools

### Phase 1: Development in Claude Chat
1. Discuss tool requirements
2. Claude asks clarifying questions (one at a time)
3. Claude explains what it will build
4. Claude asks: **"Shall I proceed?"**
5. Wait for explicit **"proceed"** confirmation
6. Claude builds tool version 1

### Phase 2: Iterative Testing
1. Download `tool-name-v1.html`
2. Save to Desktop or local folder
3. Open in browser (Chrome recommended)
4. Test all features using provided checklist
5. Report results: **"v1 worked"** or describe issues

### Phase 3: Backup & Iteration
1. When version works, Claude creates **`tool-name-v1-BACKUP.html`**
2. Backup is frozen copy, never modified
3. Next version (v2) is built FROM v1-BACKUP
4. Repeat testing cycle
5. Continue until tool is fully working

### Phase 4: Deployment
1. Upload final working version to GitHub (`/seo-tools/` repository)
2. GitHub automatically triggers Vercel deployment
3. Tool goes live at: `https://seo-tools-lake.vercel.app/tool-name.html`
4. Test live version to confirm API calls work
5. Tool is ready for production use

# TOOL ARCHITECTURE

## How Tools Work

### Frontend (HTML Files)
- Self-contained HTML files with embedded CSS and JavaScript
- Run entirely in browser
- Call Vercel API endpoints for backend operations
- Store no sensitive data locally

### Backend (Vercel API)
- Serverless functions in `/api/` folder
- Handle API calls to third-party services (Google, OpenAI, Claude, etc.)
- Protect API keys (stored in Vercel environment variables)
- Return processed data to frontend

### Data Flow:
```
User opens tool in browser
    ↓
HTML/JS calls Vercel API endpoint
    ↓
API endpoint uses environment variable (API key)
    ↓
API calls third-party service (Google, Claude, etc.)
    ↓
Third-party returns data
    ↓
API processes and returns to frontend
    ↓
Frontend displays results to user
```

# TROUBLESHOOTING

## Common Issues & Solutions

### CORS Errors
**Symptom:** "Access to fetch... has been blocked by CORS policy"

**Solution:**
- Verify API endpoint has CORS headers (see CORS Configuration section above)
- Check all 4 lines are present at top of handler function
- Ensure OPTIONS method handler is included

### API Key Errors
**Symptom:** "API key not configured" or 401/403 errors

**Solution:**
- Check Vercel environment variables are set
- Verify correct environment (Production vs. Preview)
- Confirm API key name matches code (e.g., `GOOGLE_API_KEY`)

### Tool Not Loading
**Symptom:** Tool doesn't appear after deployment

**Solution:**
- Check GitHub deployment succeeded
- Verify Vercel deployment logs (Vercel Dashboard → Deployments)
- Confirm file is in root directory (not in subfolder)
- Clear browser cache

### Registry File Conflicts
**Symptom:** Keywords showing as available when they're locked

**Solution:**
- Check `keyword-locker-registry.csv` directly in GitHub
- Verify file path in tool code
- Confirm read/write permissions
- Check for merge conflicts if multiple tools writing simultaneously

# SECURITY NOTES

## API Key Protection

**CRITICAL:** API keys are stored in Vercel environment variables, NEVER in code.

### What's Protected:
- All keys in Vercel are encrypted
- Keys never exposed in frontend code
- Keys never committed to GitHub
- API endpoints act as proxy, hiding keys from users

### Access Control:
- Only Vercel serverless functions can access environment variables
- Frontend never sees actual API keys
- Users can't extract keys from browser console
